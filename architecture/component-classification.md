# ICP + Motoko + ZenDB component classification

## Scope and reading of the evidence

This is an architecture recommendation, not an implementation plan.  **Confirmed** statements below are backed by the named current artifacts; **inferred** statements are migration conclusions from those facts; **UNKNOWN** means the source does not establish the fact.  In particular, an ICP canister's replicated state must not be treated as confidential merely because a method is not exposed publicly, and an ordinary query is not certified.

The target is deliberately small: one governance/core canister, one asset canister, existing ledger canisters where applicable, and off-chain integration workers.  ZenDB is proposed only for bounded, indexed document data; this is not a table-for-collection conversion.

## 1. Proposed canister map

1. **Core governance and treasury-policy canister** (minimum required): owns principal accounts (without private identity), eligibility, votes, holds, assessment acceptance, reserve policy, payment obligations, and public profile/assessment projections.  Public methods include principal-authenticated account-link requests, `submit_vote`, bounded `accept_assessment`, `create_payment_obligation`, governed policy changes, and read methods.  Callers are users, the asset-canister frontend, governance controllers, and authenticated off-chain workers.  Controller/governance is **UNKNOWN** and must be selected before treasury migration.  It stays one canister because its atomic policy transitions are tightly coupled.

2. **Asset canister**: owns only versioned frontend assets and public immutable files.  Its HTTP asset methods are called by browsers; release automation is its controller.  It is separate because asset storage/deployment/cache characteristics differ materially from governance state.

3. **Existing ICP Ledger/ICRC-1 ledger canisters**: own token balances and transfer execution.  The core calls them through a narrow adapter.  They cannot remain in the core because they are independent token ledgers with their own controllers, state and standards.

No additional application canister is recommended yet.  A separate treasury-execution canister is justified only if custody/governance needs an independent controller, upgrade isolation, or a policy-approved signer architecture; that evidence is currently **UNKNOWN**.

Cut over at a period boundary after atomic duplicate/eligibility tests.|Reopen legacy only for a new period; never merge simultaneous vote streams.|
|Multi-chain distribution|Private keys and reconciliation must be redesigned. Legacy is authority and executor until financial controls are accepted.|Core may shadow-calculate obligations without transfer. Cut over network-by-network after balance/conservation, idempotency and finality tests.|Pause executor and settle/reconcile the affected obligation set in the legacy process; never auto-replay unknown sends.|

## 5. Data privacy review

|Data category|Recommendation|Rationale|
|---|---|---|
|Email addresses, verification tokens, sessions, OAuth access/refresh tokens|Off-chain private storage|Direct identifiers and bearer credentials must not enter replicated state.|
|KYC payloads, personal number, issuing state, residence country, rejection reasons|Off-chain private storage; minimize to an attested eligibility flag/expiry on-chain|Government identity and sensitive decisions are unsafe on public/pseudonymous replication.|
|Private keys, mnemonic/WIF/PEM, SMTP/admin/cron/API secrets|Off-chain private storage in KMS/HSM/secret manager|A canister’s replicated state cannot safely store server secrets.|
|Raw OpenAI prompts/responses, errors and operational logs|Off-chain private storage; redact/minimize any core audit event|May include PII, credentials and large content; retention/search require protected tools.|
|Wallet addresses and social handles|Access-controlled but publicly replicated only with affirmative public-profile consent; otherwise store a hash/commitment or off-chain mapping|Addresses/handles are persistent identifiers and can reveal cross-service activity.|
|Votes, assessment/ban status, payment obligations|Access-controlled replicated storage by default; publish certified aggregate/redacted views if policy requires public auditability|These are governance/financial facts, but message/history visibility is a policy decision, not a storage accident.|
|GDP share, public display name, public leaderboard rank|Public on-chain/ZenDB projection only after documented field policy|Useful public accountability data, but do not inherit the current full-user-record exposure.|

## 6. Classification conflicts

|Case|Alternatives and trade-off|Default / evidence needed|
|---|---|---|
|Profiles: core state vs ZenDB|Core map gives maximal atomicity; ZenDB document gives indexed leaderboard/pagination. Duplicating authority risks divergence.|Core is authoritative; `public_profiles` is a derived ZenDB projection. Need scale, update-frequency and ZenDB transactional guarantees.|
|Vote records: core state vs ZenDB documents|Core map ensures one-vote atomicity; ZenDB supports rich history/search. Public messages may be unsafe.|Core keyed vote/aggregate state is default. Add a ZenDB/public view only after deciding anonymity, message publication and audit requirements.|
|Assessment evidence: embedded vs independent document|Embed is cheap/read-local but risks unbounded source/result growth; separate document permits audit/history/pagination.|Independent `assessment_runs`; embed only strict size-capped summary/sources. Need maximum result/source/evidence sizes.|
|Payment history: core map vs ZenDB|Core offers direct authoritative state; ZenDB is better for unbounded independently paginated records.|Core owns current state and immutable IDs; ZenDB collection carries history/read model if it can preserve required audit semantics. Need expected history volume and retention law.|
|GDP/price fetch: HTTPS outcall vs oracle worker|Canister outcall reduces trusted intermediary but costs cycles and has provider/response constraints; worker handles operations but adds trust.|Off-chain proposal/oracle default; direct HTTPS only for bounded public source where freshness is non-financial. Need source SLA and decision impact.|
|Treasury as core vs separate canister|Core gives atomic policy/obligation transitions; separate treasury improves custody/upgrade isolation but adds calls and complexity.|Keep policy in core. Separate only with independent custody/controller, material risk isolation, or resource evidence.|

## 7. Migration order

1. **Security and contract freeze.** Disable/restrict public logs, secret generation, distribution trigger and system-wide cleanup; document roles, field visibility, KYC retention and vote/payment policy. Dependencies: product/governance decisions. Tests: authorization matrix tests, route characterization expansion, privacy regression tests. Data: inventory/export with PII classification. Cutover: no confirmed public secret/financial/PII endpoints remain.

2. **Identity-independent public vertical slice.** Deploy asset canister and a core-owned minimal public profile/leaderboard projection. Dependencies: principal UI and approved public fields. Tests: certified/ordinary-read distinction, cursor ordering, field-redaction, upgrade persistence. Data: one-way validated export of consented public fields. Cutover: pilot cohort reads target projection; rollback serves legacy read model.

3. **Core account and governance primitives.** Introduce principal account binding, governed authorization, account lifecycle, vote uniqueness and certified public decision summaries. Dependencies: OAuth/KYC attestation design. Tests: principal ownership, duplicate vote race, period boundary, ban/hold state-machine and upgrade tests. Data: map legacy IDs to principals only after verified claim; migrate history read-only. Cutover: begin a fresh voting period on target.

4. **Evaluation proposal/acceptance.** Keep AI execution off-chain but adopt bounded, versioned results through core updates. Dependencies: worker authentication, explicit assessment policy. Tests: idempotency, malformed/oversize callback, retry/timeout, acceptance atomicity and audit trail. Data: backfill only compact accepted results/source references. Cutover: target becomes authority for newly accepted shares; raw history stays private off-chain.

5. **Treasury policy and shadow accounting.** Migrate singleton config, reserves and payment-obligation state using exact units and invariant checks; run shadow calculations without transfer. Dependencies: ratified allocation/GDP/oracle policy. Tests: conservation, status transitions, duplicate-period guard, certified public summaries. Data: reconcile legacy reserves/distributions and quarantine invalid statuses/amounts. Cutover: target is authority for obligations, not execution.

6. **Payments and operations.** First use ICRC-1 ledger adapter where applicable, then one external network at a time through hardened executor. Add scheduler/monitoring. Dependencies: custody, finality and reconciliation runbooks. Tests: crash/retry at every await boundary, idempotency, manual reconciliation, ledger/finality fixtures, disaster rollback. Data: migrate open obligations only after reconciliation. Cutover: small capped pilot with explicit pause switch; rollback pauses new execution and reconciles, never blindly retries.

This order intentionally places financial, KYC and governance-critical cutovers last while still delivering independently useful public and account slices early.
