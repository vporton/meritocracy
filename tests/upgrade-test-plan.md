# Upgrade and schema-evolution test plan

## Test discipline

Test release artifacts and deterministic stable-state serialization, not just source-level transforms. Run each scenario against the exact old and new wasm/build artifacts, an in-memory/unit fake where appropriate, and a canister-level environment with ZenDB behavior/failure injection. Use seeded fixtures that include consent withdrawal, capped documents, multiple policies/assets, terminal and nonterminal workflows, idempotency receipts, quarantine records, cursor pages and audit segments. All test suites assert bounded batch behavior and no external send from a migration.

For every supported production source version, maintain a checked-in, integrity-hashed fixture/snapshot plus its expected release manifest. When a version leaves support, keep its artifact/fixture for archival rollback rehearsal if policy requires, but do not claim it remains upgrade-compatible.

|Scenario|Setup and execution|Required assertions|
|---|---|---|
|Fresh install|Install current core and asset artifacts with empty stable state, initialize header/policy and collection metadata.|Header/version/initialization are valid; exactly one policy singleton exists; empty indexes/cursors/audit genesis are valid; only current document schemas are written; asset manifest matches release.|
|Upgrade from every supported version|For each declared source format/client/workflow version, populate its canonical fixture then upgrade to current; run all required batches and verification.|Old records decode or migrate only through declared paths; IDs, account versions, policies, receipts, audit order and public visibility remain correct; no unsupported source is accepted; N-1 client/callback contract works during its window.|
|Realistic data volume|Use capacity-approved representative account/run/vote/obligation/work/audit counts and maximum permitted document sizes/index skew. Run migration/rebuild through many batches.|Every message stays within configured item, byte and cycle bounds; cursor progresses monotonically with no duplicate/missing keys; resource/latency alert thresholds are measured; no one-message full scan occurs.|
|Pending workflows at upgrade|Create claimed/expired evaluation, identity, notification and payment work plus duplicate/out-of-order callbacks; upgrade mid-lease and resume.|IDs, expected versions, leases, receipts and schema references persist. Safe jobs reclaim only after expiry; old compatible callback replays correctly; unknown schema is rejected/quarantined.|
|Executing payment during upgrade|Create a durable `executing` obligation and simulate sent, proven-unsent and ambiguous ledger observations across upgrade.|No resend occurs before reconciliation. Sent becomes settled with unique receipt; proven-unsent alone may become retryable; ambiguity becomes `reconcile_required`; reserve/memo uniqueness holds.|
|Interrupted migration|Interrupt before row commit, after one/many row commits, after cursor commit, after upgrade checkpoint, and during ZenDB outage; restart/upgrade then resume.|Cursor never advances ahead of durable outcomes; repeated source rows replay receipts; counts are monotonic/correct; leases recover; progress/audit remains redacted and complete.|
|Repeated migration call/concurrency|Invoke same batch concurrently, retry its response, use stale expected version, and rerun a completed migration.|Only one lease/commit wins; all duplicates return stored result/status; no duplicate target/audit/index key; stale caller gets conflict; completed migration is immutable.|
|Rollback rehearsal|Create verified snapshot; exercise code-only rollback before target writes and state rollback at a controlled compatible point; separately simulate post-snapshot external send.|Manifest/hash and stable-state restore are verified; old reader works only within declared compatibility; stale ZenDB is rebuilt; post-snapshot payment is never erased and enters reconciliation; user-facing maintenance/status is accurate.|
|Index rebuild|Corrupt/delete/reorder each ZenDB index/projection generation and stable derived index in a fixture; rebuild in bounded batches.|Canonical decisions/authorized reads remain correct; rebuilt keys/count digests match canonical source; cursors reject wrong index generation; only verified generation becomes active.|
|Old-client compatibility|Run N-1 UI/client and worker callbacks against expanded core; test old cursors, record fields, errors, ordering and idempotent requests.|No breaking Candid/JSON semantic change within window; unsupported feature is capability-gated; cursors retain stable pagination or fail explicitly with version error, never mispage.|
|Post-upgrade invariant verification|Run each release’s bounded verifier over a mixed realistic fixture after migration and after projection rebuild.|All declared invariants pass: unique keys/receipts, finite statuses, policy singleton, fixed-point/integer money, reserve conservation, consent/redaction, index/projection provenance, audit continuity, bounded documents and no private content.|

## Schema-specific cases

- `public_profiles`: absent optional fields never publish consent; consent withdrawal removes/tombstones only the projection; leaderboard ties/cursors remain deterministic across index generation; unsupported public field is rejected.
- `assessment_runs`: V1 immutable accepted history retains its result/policy meaning; optional `completedAt`, URI and title-hash behavior follows lifecycle; unknown result schema is redacted/rejected rather than rescored; source caps and unique ordinals survive rebuild.
- `payment_obligations`: missing required monetary fields fail decoding; asset decimals and smallest-unit amounts never change meaning; settled requires receipt; receipt/memo/allocation uniqueness and bounded attempts survive migration; old timestamp-based duplicate data is quarantined/reconciled, not merged silently.

## Exit criteria

A release may pass the upgrade gate only when all supported-source scenarios pass, failures are triaged, migration verification is reproducible from artifacts, the rollback rehearsal meets its declared boundary, and performance demonstrates the approved batch limits. Production records the fixture/release hashes, test report, snapshot rehearsal evidence, compatible peer versions and controller approval in the release manifest/audit trail.
